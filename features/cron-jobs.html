Definition

What is a cron job?

A cron job is a scheduled task: a command that runs at fixed times, dates, or intervals.

The name comes from cron, the Unix scheduler. Schedules use a five-field cron expression: minute, hour, day of month, month, and day of week.

Traditionally you add a line to a crontab on a server that has to stay on. On Runex, each run starts its own container from your code, runs the command, and exits.

Use cron jobs for work on a clock: reports, cleanups, syncs. For work triggered by users, a background queue is the better fit.

How it works

How do cron jobs work on Runex?

Command plus schedule. That's it.

  1. You

    Pick a command

    Any script in your repo, like npm run report.

  2. You

    Set a schedule

    A cron expression, such as 0 2 * * *.

  3. Runex

    Run on time

    A container starts, runs it, and exits.

  4. Runex

    Log every run

    Output and exit status are kept.

Benefits

Example

Example: a nightly sales report

A store emails yesterday's sales to the team every morning, with no server running overnight.

  1. Add scripts/report.js to the repo
  2. Create a cron job with 0 2 * * *
  3. Set the command to node scripts/report.js
  4. At 02:00, Runex starts a container and runs it
  5. The report is emailed and the container exits
  6. Run output is saved in the job's logs

FAQ

Questions developers ask

Short answers about cron jobs. More in the documentation.

How do I write a cron expression?+

Use five fields: minute, hour, day of month, month, day of week. For example, 0 2 * * * runs at 2:00 every day, and */15 * * * * runs every 15 minutes. Runex uses this standard five-field format for scheduled jobs.

What does * * * * * mean in cron?+

Every minute. Each asterisk means “every” value for that field.

What time zone do cron jobs use?+

It depends on the platform, and many use UTC. Check the time zone shown for your schedule and convert your local time before saving it.

What happens if a cron job fails?+

The run is marked failed and its output is kept in the logs. Fix the script, and the next scheduled run picks up the change.
